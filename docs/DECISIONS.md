
# AI-Office — Архитектурные решения

**Дата начала ведения:** 24 ноября 2026 года

Этот документ содержит решения, согласованные в ходе разработки.
Новые решения добавляются в начало списка с датой и объяснением причины.

## Решение 1. Централизованное управление

**Статус:** принято.

В системе будет центральный управляющий агент — AI Director.

Пользователь взаимодействует с директором, а директор управляет специализированными сотрудниками.

## Решение 2. Специализация сотрудников

**Статус:** принято.

Каждый агент имеет:
- роль;
- описание;
- компетенции;
- уровень навыков;
- текущий статус.

Подбор исполнителя осуществляется с учётом его компетенций и доступности.

## Решение 3. Главные задачи и подзадачи

**Статус:** принято.

В системе будет иерархия:

Главная задача → Подзадачи.

На первом этапе поддерживается один уровень вложенности.

Для связи используется поле parent_task_id в модели Task.

## Решение 4. Назначения на главные задачи и подзадачи

**Статус:** принято.

Исполнители могут получать назначения:
- непосредственно на главную задачу;
- на любую подзадачу.

Главная задача может иметь собственных исполнителей одновременно с исполнителями подзадач.

## Решение 5. Правила завершения главной задачи

**Статус:** принято.

Главная задача не может считаться завершённой, пока не завершены все необходимые собственные назначения и все её подзадачи.

Пересчёт статусов должен учитывать всю иерархию.

## Решение 6. Отмена главной задачи

**Статус:** принято.

При отмене главной задачи должны отменяться её активные подзадачи и активные назначения.

Исторические данные должны сохраняться.

## Решение 7. Разделение backend и AI-логики

**Статус:** принято.

Backend отвечает за:
- сохранение данных;
- изменение статусов;
- проверку правил;
- маршрутизацию сообщений;
- выполнение технических операций.

LLM отвечает за интеллектуальные решения:
- анализ запросов;
- планирование;
- декомпозицию;
- выбор стратегии;
- оценку содержания отчётов.

LLM не должен напрямую обходить правила backend.

## Решение 8. LLM и LangGraph

**Статус:** принято как направление развития.

Подключение языковых моделей и LangGraph запланировано на третий этап.

До этого момента директор принимает решения через существующий API.

## Решение 9. Безопасность данных

**Статус:** принято.

Изменения структуры SQLite должны выполняться через безопасные миграции.

Нельзя удалять существующие задачи, назначения и историю без отдельного согласования.

## Решение 10. Порядок разработки

**Статус:** принято.

- Работа ведётся небольшими последовательными шагами.
- Перед изменениями проверяется актуальный код.
- После изменений проверяется результат.
- Завершённые сценарии не тестируются повторно без причины.
- Состояние проекта фиксируется в документации.
- При переходе в новый чат работа продолжается по документам проекта.

## Решение 11. Единый слой интеграции LLM-провайдеров

**Статус:** принято и частично реализовано.

Все AI-агенты должны взаимодействовать с языковыми моделями через единый слой LLM Manager.

Прямые обращения бизнес-логики AI-агентов к API конкретных LLM-провайдеров не допускаются.

Архитектура включает:

- `BaseLLMProvider` — общий интерфейс провайдеров.
- `LLMManager` — регистрация провайдеров, назначение моделей ролям и маршрутизация запросов.
- Реализации конкретных провайдеров — взаимодействие с API соответствующих моделей.

На текущем этапе подключён GigaChat API.

Архитектура должна поддерживать:

- подключение нескольких LLM-провайдеров;
- назначение разных моделей отдельным ролям;
- замену моделей без изменения бизнес-логики агентов;
- резервные модели и переключение при сбоях;
- локальные модели;
- централизованную конфигурацию.

При выборе провайдеров обязательным условием является возможность легального и устойчивого использования AI-Office в России.

**Принцип:** интеллектуальная логика агентов не зависит от конкретного поставщика языковой модели.
