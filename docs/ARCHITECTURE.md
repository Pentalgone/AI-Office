
# AI-Office — Архитектура системы

**Дата:** 24 ноября 2026 года

## 1. Общая архитектура

AI-Office — мультиагентная система с централизованным управлением через AI Director.

Основные компоненты:

1. Backend API — взаимодействие с системой.
2. Database — хранение задач, агентов, назначений и сообщений.
3. Task Management — управление задачами и их статусами.
4. Dispatcher — подбор и назначение исполнителей.
5. Agent Communication — обмен сообщениями и отчётами.
6. AI Director — интеллектуальное управление (будет реализован на этапе LLM).
7. Specialized Agents — специализированные исполнители.
8. Tools — внешние инструменты и интеграции (будут добавляться поэтапно).

## 2. Текущий технологический стек

- Python 3.14.
- FastAPI.
- SQLAlchemy.
- SQLite.
- Pydantic.
- Swagger / OpenAPI.

Планируемые технологии:

- LLM — языковые модели.
- LangGraph — управление многошаговой работой агентов.
- React.
- TypeScript.
- PWA.

## 3. Структура backend

Основные файлы:

- app/main.py — API-маршруты, схемы и обработчики.
- app/db/models.py — модели базы данных.
- app/db/database.py — подключение к SQLite и сессии SQLAlchemy.
- dispatcher.py — подбор исполнителей и распределение задач.
- task_manager.py — пересчёт статусов задач.

Примечание: расположение отдельных модулей необходимо сверять с актуальной структурой проекта перед изменением кода.

## 4. Основные сущности базы данных

### Agent

Представляет сотрудника AI-компании.

Основные поля:
- id
- name
- role
- description
- status
- created_at

Статусы включают:
- idle
- working
- offline

### AgentCapability

Описывает компетенции сотрудника.

Основные поля:
- id
- agent_id
- skill_code
- skill_name
- description
- level
- created_at

Используется диспетчером для подбора исполнителей.

### Task

Представляет рабочую задачу.

Основные поля:
- id
- parent_task_id
- title
- description
- status
- priority
- created_at

parent_task_id — ссылка на родительскую задачу. NULL означает, что задача является главной.

Планируемая иерархия:
Главная задача → Подзадачи.

На первом этапе поддерживается один уровень вложенности.

### TaskAssignment

Представляет назначение конкретному сотруднику.

Основные поля:
- id
- task_id
- agent_id
- assigned_by_agent_id
- instructions
- result
- status
- created_at

Одна задача может иметь несколько назначений разным сотрудникам.

Исполнители могут получать назначения как на главные задачи, так и на подзадачи.

### AgentMessage

Представляет сообщение между агентами.

Основные поля:
- id
- sender_agent_id
- recipient_agent_id
- task_id
- assignment_id
- message_type
- content
- read_at
- created_at

Используется для:
- передачи назначений;
- отправки отчётов;
- сообщений о принятии результатов;
- возврата отчётов на доработку;
- служебного взаимодействия.

### TaskEvent

Хранит историю событий задачи.

Основные поля:
- id
- task_id
- event_type
- message
- actor
- created_at

Используется для аудита и отслеживания истории выполнения.

## 5. Жизненный цикл задачи

Основные статусы задачи:

- pending
- in_progress
- completed
- failed
- blocked
- cancelled

Статусы назначений дополнительно включают:

- pending
- in_progress
- submitted
- revision_requested
- completed
- failed
- blocked
- cancelled

Пересчёт статуса задачи выполняется через task_manager.py.

Отменённая задача защищена от обычного автоматического пересчёта статуса.

## 6. Работа диспетчера

Модуль dispatcher.py отвечает за:
- поиск сотрудников по компетенциям;
- проверку уровня навыка;
- проверку доступности;
- исключение занятых сотрудников;
- создание назначения;
- создание события о назначении;
- отправку сообщения исполнителю.

В дальнейшем диспетчер будет использоваться AI Director для автоматического делегирования работы.

## 7. Отчёты и контроль результатов

Текущий механизм:

1. Исполнитель начинает назначение.
2. Исполнитель отправляет отчёт.
3. Backend сохраняет результат.
4. Назначение получает статус submitted.
5. Директор получает сообщение типа result.
6. Директор принимает результат или возвращает его на доработку.
7. Backend изменяет статус назначения.
8. Пересчитывается статус задачи.
9. Создаются сообщения и события.

В текущей версии решение директора передаётся вручную через API.

Интеллектуальная оценка содержания отчётов будет добавлена при подключении LLM.

## 8. Планируемая иерархия задач

Главная задача может содержать несколько подзадач.

Главная задача также может иметь собственные назначения исполнителям.

Правила:

- Главная задача может выполняться самостоятельно.
- Подзадачи могут выполняться параллельно.
- Подзадачи имеют собственные назначения.
- Главная задача учитывает собственные назначения и подзадачи.
- Главная задача не завершается, пока не завершены все необходимые дочерние задачи и собственные назначения.
- Отмена главной задачи распространяется на активные подзадачи и назначения.

## 9. Планируемые зависимости

В дальнейшем появится механизм зависимостей между задачами.

Пример:

- Сначала Researcher собирает информацию.
- После завершения исследования Analyst выполняет анализ.
- После анализа Writer готовит итоговый документ.

Задача, ожидающая другую задачу, не должна начинаться до выполнения необходимых условий.

Конкретная модель зависимостей будет согласована отдельно.

## 10. Будущий AI Director

AI Director должен стать центральным интеллектуальным компонентом.

Его функции:

- анализ запросов пользователя;
- планирование;
- декомпозиция;
- определение компетенций;
- делегирование;
- контроль зависимостей;
- мониторинг выполнения;
- анализ отчётов;
- запрос доработок;
- перепланирование;
- формирование итоговых результатов.

Планируемая основа оркестрации — LangGraph.

## 11. Принципы развития архитектуры

1. Не смешивать задачи и назначения.
2. Не смешивать интеллектуальные решения LLM и технические операции backend.
3. Все важные изменения статусов журналировать.
4. Сохранять историю сообщений и результатов.
5. Не допускать завершения родительской задачи при незавершённых обязательных работах.
6. Учитывать ошибки и отмены.
7. Поддерживать расширение состава сотрудников.
8. Изменения базы проводить безопасными миграциями.
9. Сохранять совместимость уже работающих API там, где это возможно.


## 8. Архитектура пользовательского интерфейса Pixel Office

### 8.1. Основной принцип

Пользовательский интерфейс AI-Office представляет собой интерактивный пиксельный офис, визуально ориентированный на Lumio для Mac.

Офис является визуальным представлением работающей мультиагентной системы. Он не должен существовать отдельно от backend и показывать вымышленную деятельность.

### 8.2. Разделение архитектуры

Система состоит из трёх основных уровней:

1. Backend — хранит задачи, назначения, сотрудников, сообщения, события и фактические состояния.
2. AI-логика — принимает решения, выполняет задачи, взаимодействует с инструментами и другими агентами.
3. Pixel Office UI — визуализирует состояние системы и предоставляет пользователю инструменты управления.

### 8.3. Визуальная модель сотрудника

Каждый сотрудник должен иметь визуального персонажа и рабочее место.

Интерфейс отображает:
- имя и должность;
- специализацию;
- текущее состояние;
- текущую задачу;
- прогресс выполнения;
- последнюю активность;
- историю действий и взаимодействий.

### 8.4. Состояния и анимации

Визуальное состояние персонажа определяется реальным состоянием сотрудника и его назначений.

Предусмотреть состояния:
- idle — ожидает работу;
- working — выполняет задачу;
- researching — проводит исследование;
- analyzing — анализирует данные;
- writing — создаёт материалы;
- communicating — взаимодействует с другими агентами;
- reviewing — проверяет результат;
- blocked — заблокирован или ожидает зависимость;
- offline — недоступен.

Список визуальных состояний может расширяться по мере развития системы.

Backend не должен зависеть от конкретной анимации. Между внутренними статусами системы и визуальными состояниями необходимо предусмотреть отдельный слой преобразования.

### 8.5. Данные для интерфейса

В будущем потребуется API для получения:
- списка сотрудников;
- состояния сотрудников;
- списка задач и подзадач;
- назначений и исполнителей;
- прогресса выполнения;
- событий и истории активности;
- сообщений и передачи результатов;
- общей статистики компании.

Для обновления интерфейса в реальном времени следует предусмотреть WebSocket или другой подходящий механизм обновления данных.

### 8.6. Основные элементы интерфейса

- Пиксельная карта офиса с рабочими местами.
- Персонажи сотрудников и анимации их деятельности.
- Карточка выбранного сотрудника.
- Панель задач и подзадач.
- Лента событий компании.
- Панель директора и постановки новых задач.
- Общий индикатор прогресса и состояния компании.

### 8.7. Технические принципы

- Предполагаемый frontend: React + TypeScript.
- Backend остаётся источником достоверного состояния.
- UI не принимает решения за AI-агентов.
- Визуальные действия соответствуют реальным событиям системы.
- Анимации не должны блокировать выполнение задач.
- Архитектура должна позволять добавлять новых сотрудников, роли, состояния и элементы офиса без полной переработки интерфейса.

### 8.8. Критерий архитектурной готовности

Pixel Office должен получать данные из реальной мультиагентной системы и отображать фактическую деятельность сотрудников, задач и директора. Пользователь должен иметь возможность наблюдать за компанией и управлять её работой через интерфейс.

## 9. Архитектура интеграции языковых моделей (LLM)

### 9.1. Общая архитектура

Для взаимодействия AI-агентов с языковыми моделями используется независимый от конкретного провайдера слой LLM.

Основные компоненты:

- `BaseLLMProvider` (`app/llm/base.py`) — базовый интерфейс всех LLM-провайдеров.
- `GigaChatClient` (`app/llm/gigachat.py`) — реализация взаимодействия с GigaChat API.
- `LLMManager` (`app/llm/manager.py`) — регистрация провайдеров, назначение моделей ролям и маршрутизация запросов.

### 9.2. Принцип работы

Поток взаимодействия:

1. AI-агент обращается к LLM Manager с указанием своей роли и текстом запроса.
2. LLM Manager определяет назначенного провайдера и модель.
3. Запрос передаётся соответствующему LLM-провайдеру.
4. Провайдер выполняет авторизацию и отправляет запрос к API модели.
5. Ответ возвращается агенту через LLM Manager.

Таким образом, бизнес-логика AI-агентов не должна зависеть от особенностей конкретного LLM API.

### 9.3. Требования к провайдерам

Каждый новый провайдер должен реализовывать интерфейс `BaseLLMProvider`.

Текущий метод интерфейса:

- `chat(message, model)` — асинхронная отправка сообщения модели и получение текстового ответа.

При добавлении провайдера не требуется переписывать логику AI-агентов.

### 9.4. Конфигурация моделей

Модели назначаются отдельным ролям AI-агентов.

Предусматривается возможность:

- использовать разные модели для разных ролей;
- менять провайдера без изменения бизнес
